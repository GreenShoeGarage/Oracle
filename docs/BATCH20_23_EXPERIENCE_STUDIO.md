# Batches 20–23 — Experience Studio

ORACLE v2.3.0 · SQL schema 16 · September 8, 2026

## Release scope and acceptance boundary

This software release includes the previously verified Batch 19 Command Deck and the Batches 20–23 implementation. **The Batch 20 field-proven acceptance milestone is still open.** Automated tests, an isolated load rehearsal, emulated layouts, and a successful deployment do not prove a physical-device or human field pilot, a scheduled live backup, a real-data recovery, an application rollback, or sustained Railway capacity. The release number does not certify those observations.

The user requested proceeding with the later software batches while retaining that explicit distinction. New scenario sizes and durations remain design targets, not field-validated claims. No behavioral analytics, engagement scoring, leaderboards, automatic roleplaying judgments, or generic automation engine were added.

## Entry and everyday use

Open an event in **Organizer view → Experience Studio**. The workspace is integrated with the existing sidebar, event overview, account protections, theme, reading controls, and unsaved-navigation guards.

Four tabs cover **Scenario library**, **Experience builder**, **Packs & versions**, and **Field checks**. Installation is available only for draft and rehearsal events. Existing live events continue using their original content; they are not populated automatically.

### Batch 20: record evidence, do not manufacture readiness

Field checks provides twelve deliberately unrun checks covering physical iPhone and Android offline reopening, camera/manual codes, accessibility, newcomers, lower-pressure participation, organizer use, rehearsal reset, scheduled live backups, isolated recovery of a live backup, a schema-compatible application rollback, and sustained Railway measurements.

Each pass needs an observer, observation timestamp, tested target, and evidence. Physical checks require a physical-device declaration. A complete report additionally needs a full tested commit, the current release, and explicit human attestation. Unresolved critical or major findings remain blockers even when scheduled. Findings can be recorded and edited in the workspace; reports can be imported/exported as a separate JSON format. Saves use optimistic revisions. Reports are organizer-only and explicitly self-reported, not independently verified certificates.

Release evidence remains separate: the application suite, full application-module/DOM/HTTP journey, immutable-shell checks, and disposable database recovery all have their own test output. Local browser network navigation was restricted, so Chromium checks use in-memory layout rendering, not a real-browser network journey. Physical-device, assistive-technology and human acceptance are not closed by those renders.

### Batch 22: guided authoring

Six steps cover **Setup → People → Personal arcs → Shared goal → Instruments → Ending & review**. Organizers edit actual template fields and add/remove bounded roles, cards, arcs, contribution routes, milestones, resource dependencies, instruments, and consequences. A saved draft has an independent optimistic revision, distinct from a pack’s portable version number.

Local checks identify malformed content, reference cycles, missing prerequisites, impossible distinct-player counts, insufficient lower-pressure openings, and a limited number of independent contribution routes. Server preview additionally validates event/theme/lifecycle, current resource and character mappings, published resource dependencies, required ending roles, available capacity for definitions, and adventure play history. Existing adventure progress prevents appending new nodes until the organizer uses a fresh event or resets a dedicated rehearsal.

Role mappings validate organizer assignment suggestions and ending prerequisites; they **do not** impersonate players, automatically assign a relationship, or bypass consent. Resource mappings point to resources already defined in the destination event. The installer creates neither balances nor donations.

Preview describes all new records and required instrument activation. Confirmation is tied to the reviewed pack, mappings, event/adventure revisions, and installation history. A changed preview must be reviewed again. Required instrument activation is an explicit choice. Everything commits atomically; partial definitions are rolled back on failure.

Draft text stays in page memory, including during interrupted requests. Edits typed while a save is running remain marked unsaved after the submitted revision returns. Export before leaving a disconnected page. Account or authority loss clears private authoring data; a late response cannot replace another account’s or event’s workspace.

### Batch 23: reusable authored packs

The portable format is `oracle-experience-pack`, format version `1`, with a maximum serialized size of 400 KB. It is deliberately different from legacy format-1 briefing packs, player journal exports, Field desk notes, and full database backups.

Import opens an editable preview only. Export contains authored fiction—including organizer notes, puzzle answers and endings—and therefore is intended for organizers. **Print player prompts** omits hidden readings, puzzle answers, organizer notes and endings; its generic openings are not assigned or mutually accepted facts.

Pack version 1 supports four authored instrument types (RELIC, DEAD DROP, CIPHERBOX, WAYFINDER), three milestone modes (reviewed, verified evidence, resource units), the existing RELIC/DEAD DROP/SIGIL/OATHBOOK evidence adapters, and two explicit event-wide consequences (content unlock and BROADSIDE draft). SIGIL/OATHBOOK declarations refer to eligible outcomes from those existing tools; their full authoring definitions are not serialized in this pack format. Only the four listed instrument definitions are portable here. Arbitrary scripts, CSS, executable formulas, foreign event/player IDs, unknown keys, sparse structures, and future format versions are rejected. Stories are rendered as escaped text.

Every installation creates fresh record IDs and fresh prop codes, with prerequisite/resource mappings resolved in the destination. The original document, digest, version, and local mapping remain recorded. An exact same-key/version/content/choice retry returns the existing installation. Reusing that version with different content is a conflict.

**Upgrades are additive, never in-place.** A newer version requires a comparison preview and explicit confirmation that it will be installed alongside the old version. Customized existing definitions and all play history stay untouched. Current cards, arcs, projects and nodes report edited/missing indicators where tracked. There is no automatic merging of edits or deletion of removed older content. The organizer decides which old material to retire through its original tools.

**Open original authored pack** exports the exact Studio snapshot as installed. Subsequent edits made directly in Characters, Connections, Arcs, Projects, or Adventure tools are not reverse-engineered into that snapshot. They are preserved in the event and surfaced as customization warnings. Edit/export the Studio draft to create a portable revised edition; use full database recovery for an operational backup.

## Rehearsal and recovery

Rehearsal copying now includes current authored engagement definitions, pack drafts, and installation provenance with new record IDs. Existing adventure IDs remain event-scoped while prop codes are regenerated by the established copier. Character-linked consequence audiences are remapped without broadening access. Source consent, connection responses, personal arc progress, contributions, donations, rewards, effects, refunds and field-acceptance reports are not inherited.

Dedicated rehearsal reset clears its engagement play receipts and generated effects alongside the existing inventory baseline reset. It never resets the source event. Existing player Field desk notes remain governed by their original device-local rules; the server does not claim to erase information already seen or copied offline.

Migration 016 adds `experience_pack_drafts`, `experience_pack_installs`, and `field_acceptance_reports`. Existing schemas are upgraded additively. The recovery fixture explicitly populates all three tables and compares restored contents. Startup requires schema 16: **do not roll back to a schema-15 application binary against this database**. Recover with a verified schema-16-compatible roll-forward release until a compatible application rollback has actually been rehearsed. The application rollback acceptance check remains open.

## Verification

Focused tests cover strict format validation, all fifteen library documents, graph/resource/role dependencies, author-only scope, optimistic saves, exact retries, simultaneous installs, additive upgrades preserving customizations, current authority, expected-account isolation, stale preview rejection, lifecycle boundaries, field-report evidence rules, saved/unsaved UI states, HTML escaping, offline behavior and stale responses.

A complete new-pack journey proves discovery → deliberately submitted evidence → reviewed contributions → one completion → permitted ending and draft bulletin. Copy/reset checks preserve source completion. The remote staging journey repeats this for Fantasy, Cyberpunk, and Wasteland. Production checks remain read-only. The v2.3 public offline shell includes all new modules and retains the complete inherited application chain; private Studio and Command Deck responses are never service-worker cached.

The next step after software deployment is still actual field and operations validation—not marking Batch 20 complete from the release number.
